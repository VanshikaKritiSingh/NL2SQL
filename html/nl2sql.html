NL2SQL Pipeline: Production Architecture

Design draft for team review, v2 · diagram and legend inlined · headings Playfair/Fraunces, body Inter/Helvetica · stage numbers in the diagram match section 3

1. Overview

A human-supervised natural-language-to-SQL pipeline: users query and modify a database in plain English, and the agent never touches the database directly. Every generated statement is validated, parameterized, and converted to the target dialect, then submitted to the DBMS the user already runs: MySQL, Oracle, SQL Server, Microsoft Access, or similar. The DBMS executes the statement and applies the change. The pipeline's only data touchpoint is that DBMS, so the user's existing permissions, roles, and auditing stay in force.

Core loop: query → cache check → generate SQL → validate → estimate cost/risk → route by risk tier → human approval (writes only) → submit to the user's DBMS → execute → return results. Every sub-project in section 4 strengthens exactly one stage of this loop.

3. Stage-by-stage walkthrough

#StagePurpose
1Rate / budget limiterBlocks runaway per-user request volume before any cost is incurred.
2Semantic cacheSkips model, validation, and execution when a semantically equivalent question was already answered.
3Schema linking / RAG retrievalHands the model only the relevant tables, not the full schema, so prompts stay bounded on large databases.
4Deep learning modelGenerates candidate SQL from the query, plus retry feedback when looping.
5Injection sanitizerForces the SQL through a parameterized query builder; no raw string concatenation.
6Dialect converterDeterministically normalizes SQL to the dialect of the user's specific DBMS; MySQL, Oracle, SQL Server, and Access SQL differ.
7Static validatorChecks syntax, schema validity, and known anti-patterns before anything is costed or executed.
8Retry gateBounded loop: after N failed attempts, escalate instead of retrying forever.
9Cost / risk gateEXPLAIN-style dry run issued through the DBMS estimates cost and rows scanned; anything over threshold is rejected or escalated.
10Risk tier routerRead-only queries auto-execute on a sandbox replica (same DBMS, read-only role); mutating / DDL statements go to human review.
11ER diagram / impact visualizerShows the reviewer what the statement will touch before approval.
12Human approval gateRequired for writes and schema changes only, not for every query.
13Transaction wrapper + checkpointWraps approved writes in a transaction with a rollback point.
14Schema version controlTracks every committed change like a migration log, for audit and rollback; migrations are applied through the DBMS.
15User's DBMSThe pipeline's only touchpoint with stored data: it submits the parameterized, dialect-correct statement to the DBMS the user already runs, and the DBMS executes it and applies the change. The pipeline holds no direct data access; existing DBMS permissions and roles stay in force.
16Audit logSide channel every stage writes to: queries, decisions, outcomes. Not a stage requests pass through.

Deliberately excluded (good tools, no per-query tie-in to this pipeline): automated schema-from-ER generation, multivalued-dependency visualizer, denormalization advisor, step-by-step normalization pipeline (schema-design phase); workload re-player, schema-drift detector, vector index extension, warehouse-free analytics dashboard (ops / infrastructure, orthogonal to NL2SQL).

5. Production practices baked in

  • Submit through the user's DBMS, never around it. The agent's only data touchpoint is the DBMS the user already runs; it submits validated, parameterized SQL and the DBMS alone executes statements and changes data. No direct file or storage access, so existing permissions, roles, and auditing stay in force. [4][5]
  • Cache before you generate. Compare the query embedding against previously answered queries; on a high-confidence match, return the cached response and skip model, validation, and execution. [1][2]
  • Narrow the schema before generation. Classify intent and extract entities first, then map to the relevant tables only; scales past what fits in a prompt. [3]
  • Bound every retry loop. Invalid-then-retry needs a max count with an explicit escalation path; unbounded loops are production incidents. [4]
  • Estimate cost before you execute. EXPLAIN-style dry run through the DBMS plus per-user rate / budget limits; reject or escalate anything over a cost / scan threshold. [4]
  • Tier risk instead of gating uniformly. Reads run automatically, medium risk notifies, writes and DDL need sign-off; uniform gating over-blocks or under-protects. [5][6]
  • Wrap writes in a transaction with a checkpoint. A failed long-running process resumes from its last known-good state instead of restarting blind. [7]
  • Log everything as a side channel. Layered controls: policy checks, scoped roles, human approval on high-impact actions; every decision logged for accountability. [5]
  • Treat readiness as context and governance, not syntax. Business context, query governance, and iterative follow-up support decide success more than raw SQL-writing ability; hence the weight on stages 3, 10, and 16. [8]

6. Implementation phasing

  • Day one (cheap to build, removes entire risk classes): per-user rate limiter, parameterized query builder / sanitizer, read-only sandbox replica (same DBMS, read-only role), bounded retry gate.
  • Fast-follow (needs real query volume to tune): semantic cache similarity threshold, cost / EXPLAIN gate calibration, index advisor.
  • Ongoing / offline: fuzz harness against the validator, anti-pattern detector as a scheduled review job.
